# Подписки на Stripe: настройка, проверка, запуск

Пошаговый гайд для того, кто разворачивает приложение. Код подписок уже написан и работает —
здесь только то, что нужно сделать руками в Stripe и в переменных окружения.

Если Stripe не настроен, приложение работает как раньше: пользователям доступен бесплатный
лимит (один тест), а кнопки покупки на `/pricing` отключены с пояснением. Так что настраивать
можно не спеша и не ломая рабочий сайт.

## Что понадобится

- Аккаунт [Stripe](https://dashboard.stripe.com) (регистрация бесплатная).
- Домен с HTTPS для продакшена — Stripe шлёт вебхуки только на публичный адрес.
- [Stripe CLI](https://stripe.com/docs/stripe-cli) для локальной проверки.
- Уже настроенные `GEMINI_API_KEY` и ключи Clerk (см. основной README).

> **Главное про режимы.** У Stripe есть тестовый режим (в новых аккаунтах он называется
> **Sandbox** — вверху висит синяя полоса «You're testing in a sandbox») и боевой. Они полностью
> раздельны: свои ключи, свои цены с **другими** price id, свой вебхук, своя настройка портала.
> Всё, что вы сделаете в песочнице, придётся повторить в боевом аккаунте — кнопкой
> **Switch to live account** в той же полосе.

Начинайте в **тестовом** режиме.

## Шаг 1. Создать три цены

В дашборде Stripe: **Product catalogue** (Каталог товаров) → **Add product**.

Создайте три товара — по одному на тариф:

| Товар | Цена | Периодичность |
|---|---|---|
| Janob IELTS Starter | $20.00 | Monthly (recurring) |
| Janob IELTS Pro | $60.00 | Monthly (recurring) |
| Janob IELTS Max | $100.00 | Monthly (recurring) |

Два обязательных условия:

- **Тип цены — Recurring (повторяющийся), период Monthly.** Если создать одноразовую
  (one-off) цену, оформление подписки упадёт с ошибкой: приложение открывает Checkout в режиме
  `subscription`, а он принимает только повторяющиеся цены.
- **Валюта — USD**, потому что тарифы в коде описаны в долларах.

### Где взять price id

На странице товара price id нигде не написан крупно — он спрятан в строке самой цены.
Откройте товар и в блоке **Pricing** нажмите **···** в конце строки с ценой →
**Copy price ID**. В буфер попадёт строка вида `price_1Q…`.

Если такого пункта в меню нет, кликните по самой строке с ценой: откроется страница цены, и её
id будет виден и в адресной строке (`…/prices/price_1Q…`), и внизу на панели разработчика.

> ⚠️ **Product ID (`prod_…`) не подходит.** Он крупно написан в панели **Details** справа, и
> именно его копируют по ошибке чаще всего. Приложению нужен `price_…` — с product id
> оформление подписки не заработает.

## Шаг 2. Взять секретный ключ

**Developers** → **API keys** → **Secret key** → Reveal.

В тестовом режиме ключ начинается с `sk_test_…`, в боевом — с `sk_live_…`.

Этот ключ даёт полный доступ к деньгам: он живёт только в переменных окружения сервера,
никогда не попадает в браузер и никогда не коммитится в git.

## Шаг 3. Включить Customer Portal

**Где искать:** шестерёнка ⚙️ справа вверху, рядом с колокольчиком → раздел **Billing** →
**Customer portal**. Прямая ссылка: `https://dashboard.stripe.com/test/settings/billing/portal`
(для боевого аккаунта — тот же адрес без `/test/`).

> В левом меню под **Billing** портала нет: это настройки аккаунта, а не раздел биллинга.
> Там вы найдёте Overview, Subscriptions, Invoices и прочее, но не портал.

Отметьте то, что пользователь может делать сам:

- обновлять платёжный метод (карту);
- отменять подписку;
- переключаться между тарифами — в секции **Subscriptions** включите «Customers can switch
  plans» и добавьте все три цены из шага 1. Без этого пользователь сможет только отменить
  подписку и поменять карту, но не перейти с $20 на $60 прямо в портале.

> Кнопку **Activate test link** нажимать не нужно: это готовая ссылка на портал для тех, кто
> не пишет интеграцию. Приложение открывает портал само, через API, и ему достаточно
> сохранённой конфигурации. Переключатель «Enable next generation portal experience» тоже можно
> не трогать.

Нажмите **Save changes** — обязательно, даже если ничего не меняли. У аккаунта должна быть
конфигурация портала по умолчанию: в блоке **Portal configuration** рядом с «Default» виден её
id вида `bpc_…` — значит, она есть. Если её нет, Stripe отказывается создавать сессию
(`No configuration provided`), и кнопка «Обунани бошқариш» / «Manage subscription» на
`/pricing` падает с ошибкой.

Настройку портала нужно сохранить **отдельно в песочнице и отдельно в боевом аккаунте**.

## Шаг 4. Настроить вебхук

Вебхук — это то, как приложение узнаёт об оплате. Без него деньги спишутся, а тариф
у пользователя не появится.

### Локально

Stripe не достучится до `localhost`, поэтому события пробрасывает CLI:

```bash
stripe login
stripe listen --forward-to localhost:3000/api/billing/webhook
```

CLI напечатает секрет подписи вида `whsec_…` — это **локальный** `STRIPE_WEBHOOK_SECRET`.
Он свой на каждый запуск `stripe listen` и **не совпадает** с продовым.

Оставьте `stripe listen` работать в отдельном терминале, пока тестируете.

### На продакшене

**Developers** → **Webhooks** → **Add endpoint**.

- **Endpoint URL:** `https://ваш-домен/api/billing/webhook`
- **События** — ровно эти восемь:

```
checkout.session.completed
customer.subscription.created
customer.subscription.updated
customer.subscription.deleted
customer.subscription.paused
customer.subscription.resumed
invoice.paid
invoice.payment_failed
```

После создания откройте эндпоинт и скопируйте **Signing secret** (`whsec_…`) — это продовый
`STRIPE_WEBHOOK_SECRET`.

Эндпоинт вебхука намеренно открыт без авторизации (`src/proxy.ts`): Stripe приходит не с
сессией пользователя, а с подписью. Каждый запрос проверяется по этой подписи, и всё, что
подписано неверно, отбрасывается до единой строчки обработки.

## Шаг 5. Прописать переменные окружения

В `.env.local` (локально) и в переменных окружения хостинга (на проде):

| Переменная | Обязательна | Что это |
|---|---|---|
| `STRIPE_SECRET_KEY` | да | Секретный ключ из шага 2 |
| `STRIPE_WEBHOOK_SECRET` | да | Секрет подписи из шага 4 |
| `STRIPE_PRICE_STARTER` | да | `price_…` тарифа $20 |
| `STRIPE_PRICE_PRO` | да | `price_…` тарифа $60 |
| `STRIPE_PRICE_MAX` | да | `price_…` тарифа $100 |
| `NEXT_PUBLIC_APP_URL` | нет | Абсолютный адрес сайта. Нужен, только если за прокси заголовки хоста приходят неверные и Stripe возвращает пользователя не туда |
| `BILLING_LIVE_TOKENS_PER_SECOND` | нет | Сколько токенов в секунду стоит живая сессия. По умолчанию `100`, см. [подгонку тарифов](#подгонка-размеров-тарифов) |

Пример:

```bash
STRIPE_SECRET_KEY=sk_test_51Qxxxxxxxxxxxx
STRIPE_WEBHOOK_SECRET=whsec_xxxxxxxxxxxx
STRIPE_PRICE_STARTER=price_1QaaaaaaStarter
STRIPE_PRICE_PRO=price_1QbbbbbbPro
STRIPE_PRICE_MAX=price_1QccccccMax
```

После изменения переменных перезапустите `npm run dev`, а на проде — пересоберите и
перезапустите приложение.

Если какой-то из трёх `STRIPE_PRICE_…` пуст, соответствующий тариф просто нельзя будет купить,
остальные продолжат работать.

## Шаг 6. Проверить локально

Понадобятся три терминала: `npm run dev`, `stripe listen` и один свободный.

**1. Проверьте расчёт токенов — он не требует ни сервера, ни Stripe:**

```bash
npx tsx scripts/check-billing.ts
```

Должно вывести `17 checks passed`.

**2. Откройте `/pricing`.** Вы должны увидеть четыре карточки тарифов, текущий тариф Free и
полоску расхода. Если висит жёлтый баннер «To'lov tizimi hali ulanmagan» — Stripe не подхватился,
проверьте `STRIPE_SECRET_KEY` и price id.

**3. Оформите подписку.** Нажмите «Pro тарифини танлаш», на странице Stripe введите тестовую
карту:

```
Номер:  4242 4242 4242 4242
Срок:   любая будущая дата (например 12/34)
CVC:    любые три цифры
Индекс: любой
```

Другие тестовые карты (отказ, 3-D Secure) — в [документации Stripe](https://stripe.com/docs/testing).

**4. Проверьте возврат.** Вас вернёт на `/pricing?checkout=success&plan=pro`. Пару секунд будет
висеть «To'lov qabul qilindi — tarif faollashtirilmoqda…», пока прилетает вебхук, затем тариф
сменится на Pro, а лимит станет 7.8M токенов. Страница сама опрашивает состояние примерно
24 секунды.

В терминале со `stripe listen` в это время должны пробежать `checkout.session.completed`,
`customer.subscription.created` и `invoice.paid` — все со статусом `200`.

**5. Проверьте счётчик.** Пройдите тест: в боковой панели полоска расхода должна вырасти.

**6. Проверьте портал.** Нажмите «Обунани бошқариш» — откроется портал Stripe, где можно
сменить карту, тариф или отменить подписку. Отмените подписку и вернитесь: на `/pricing`
появится плашка «Тарифингиз … да тугайди ва янгиланмайди».

**7. Проверьте упор в лимит** (необязательно, но полезно). Временно уменьшите тарифы в
`src/lib/billing/plans.ts`, пройдите тест и убедитесь, что вместо кнопки старта появляется
карточка «Токенларингиз тугади» со ссылкой на тарифы. Не забудьте вернуть значения обратно.

## Шаг 7. Перейти в live-режим

Переключите дашборд Stripe в боевой режим и повторите шаги 1–5:

- [ ] Активировать аккаунт Stripe (реквизиты компании, банковский счёт) — без этого боевой
      режим не принимает платежи.
- [ ] Создать три цены заново. **Их price id будут другими** — обновите `STRIPE_PRICE_…`.
- [ ] Взять боевой `sk_live_…` ключ.
- [ ] Сохранить конфигурацию Customer Portal в боевом режиме.
- [ ] Создать вебхук на боевой домен, взять новый `whsec_…`.
- [ ] Прописать все пять переменных в окружении хостинга и перезапустить приложение.

Полный список переменных для деплоя (вместе с Gemini и Clerk) — в основном README, раздел
«Деплой».

## Чек-лист перед публичным запуском

- [ ] `npx tsx scripts/check-billing.ts` проходит.
- [ ] Боевые цены — recurring monthly, в USD, price id совпадают с переменными.
- [ ] Вебхук в боевом режиме отвечает `200` (вкладка эндпоинта → последние доставки).
- [ ] Customer Portal настроен в боевом режиме.
- [ ] Пройден один реальный платёж настоящей картой на небольшой тариф — и возвращён через портал.
- [ ] На ключе Gemini стоит бюджет и оповещения о расходах. Тарифы ограничивают каждого
      пользователя, но общий потолок по проекту всё равно нужен.
- [ ] `TOKENS_PER_TEST` и `BILLING_LIVE_TOKENS_PER_SECOND` сверены с реальным расходом
      (см. следующий раздел) — иначе тарифы могут оказаться щедрее или скупее, чем задумано.

## Подгонка размеров тарифов

Все размеры тарифов выводятся из одной константы — `TOKENS_PER_TEST` в
`src/lib/billing/plans.ts`:

```ts
export const TOKENS_PER_TEST: Record<ExamMode, number> = { full: 120_000, quick: 60_000 };
```

Это **оценка**, сделанная до наблюдения реального расхода. От неё зависят и размеры тарифов, и
сколько токенов резервируется на старте теста, и надпись «≈ 20 тестов» на странице тарифов.

### Как измерить реальный расход

Браузер присылает фактический расход живой сессии на `/api/exam/usage`. Чтобы его увидеть,
временно добавьте лог в `src/app/api/exam/usage/route.ts`, рядом с вызовом `settleExam`:

```ts
console.log("[usage]", { examId, tokens });
```

Пройдите 3–5 полных тестов и 2–3 быстрых, соберите цифры из логов. Расход на распознавание и
оценку виден там же — поставьте такой же лог в `chargeUsage` (`src/lib/server/billing/account.ts`).

Сверить общую картину можно в консоли Google AI Studio / Google Cloud по расходу ключа Gemini.

### Что править по результатам

1. **`TOKENS_PER_TEST`** — средний полный расход теста (живая сессия + распознавание + оценка).
2. **`BILLING_LIVE_TOKENS_PER_SECOND`** — средний расход живой сессии, делённый на её
   длительность в секундах. Меняется переменной окружения, без пересборки кода.
3. **Размеры тарифов** в `PLANS` — если хотите сохранить обещание «≈ 20 / 65 / 115 тестов»,
   пересчитайте `tokens` как `число тестов × TOKENS_PER_TEST.full`.

После правки прогоните `npx tsx scripts/check-billing.ts` — проверка размеров тарифов там
зафиксирована и сразу скажет, если цифры разъехались с обещаниями на странице.

### Про экономику

По оценке из README один полный тест обходится в $0.15–0.30 у Google. Тариф Starter за $20
даёт примерно 20 тестов, то есть около $4–6 себестоимости. Запас заложен намеренно: он
покрывает тесты, которые пользователь бросил на середине, повторные попытки и разброс
длительности. Если будете менять размеры тарифов — считайте от этой себестоимости, а не от
числа тестов.

## Если что-то не работает

### На `/pricing` жёлтый баннер, кнопки покупки неактивны

Приложение не видит настроенного Stripe. Проверьте, что заданы `STRIPE_SECRET_KEY` и хотя бы
один `STRIPE_PRICE_…`, и что приложение перезапущено после правки переменных.

### При нажатии на тариф — ошибка

Смотрите логи сервера, там будет строка `[billing/checkout]` с настоящей причиной. Обычно это:

- в `STRIPE_PRICE_…` попал product id (`prod_…`) вместо price id (`price_…`);
- цена не recurring, а одноразовая;
- price id из тестового режима, а ключ — боевой (или наоборот).

### Оплата прошла, но тариф не появился

Проблема в вебхуке. Откройте **Developers → Webhooks → ваш эндпоинт → последние доставки**:

- **Доставок нет вообще** — эндпоинт создан не на том домене или не подписан на нужные события.
- **Доставка с кодом 400 `invalid_signature`** — не тот `STRIPE_WEBHOOK_SECRET`. Частый случай:
  в окружении лежит локальный секрет из `stripe listen`, а не продовый (или наоборот).
- **Код 500 `sync_failed`** — приложение не смогло записать состояние; смотрите логи сервера,
  Stripe повторит доставку сам.
- **Код 200, но тариф всё равно Free** — цена, на которую оформлена подписка, не совпадает ни
  с одним из трёх `STRIPE_PRICE_…`. Подписка на неизвестную цену не даёт никакого тарифа.

Можно не ждать: приложение само перечитывает подписку из Stripe, если запись выглядит
устаревшей (период кончился или идут повторные попытки списания), не чаще раза в минуту.

### Кнопка «Обунани бошқариш» выдаёт ошибку

Не сохранена конфигурация Customer Portal в текущем режиме Stripe — вернитесь к шагу 3.

### После оплаты вернуло не на тот домен

Приложение строит адреса возврата из заголовков запроса. Если за прокси они приходят неверными,
задайте `NEXT_PUBLIC_APP_URL=https://ваш-домен`.

### Лимит не обновился в новом месяце

Должно прилететь `invoice.paid` — проверьте доставки вебхука. Даже если событие потерялось,
приложение перечитает подписку из Stripe при первом обращении после конца периода.

### У пользователя `limit_reached` при старте теста

Это не ошибка, а исчерпанный лимит: пользователь увидит карточку со ссылкой на тарифы. Текущий
расход виден в полоске в боковой панели и на `/pricing`.

### Пользователь отменил подписку и хочет снова бесплатный тест

Так не работает намеренно. При возврате на Free счётчик расхода сохраняется — иначе цикл
«подписался → отменил» выдавал бы бесконечные бесплатные тесты. Счётчик обнуляется только с
началом нового оплаченного периода.

## Как это устроено внутри

Подробное описание — в README, раздел «Подписки и учёт токенов». Здесь коротко, куда смотреть.

### Маршруты

| Маршрут | Что делает |
|---|---|
| `GET /api/billing/me` | Текущий тариф и расход для интерфейса |
| `POST /api/billing/checkout` | Создаёт сессию Stripe Checkout, возвращает ссылку |
| `POST /api/billing/portal` | Создаёт сессию Customer Portal |
| `POST /api/billing/webhook` | Принимает события Stripe (без авторизации, по подписи) |
| `POST /api/exam/usage` | Отчёт браузера о расходе живой сессии |
| `POST /api/live/token` | Резервирует стоимость теста и выдаёт токен сессии; `402`, если лимита нет |

### Файлы

```
src/lib/billing/plans.ts          каталог тарифов и TOKENS_PER_TEST
```

### Поток оплаты

```
Пользователь → /pricing → POST /api/billing/checkout
  → Stripe Checkout (карта)
  → Stripe шлёт webhook → /api/billing/webhook
       → приложение перечитывает подписку из Stripe и сохраняет её
  → пользователя возвращает на /pricing?checkout=success
       → страница опрашивает /api/billing/me, пока не увидит новый тариф
```

### Поток учёта токенов

```
Старт теста  → POST /api/live/token
                 резерв 120K (полный) / 60K (быстрый); нет лимита → 402
Идёт тест    → браузер напрямую говорит с Gemini, копит usageMetadata
Конец теста  → POST /api/exam/usage { examId, tokens }
                 сервер зажимает цифру: не меньше нижней границы по реальной
                 длительности сессии, не больше потолка по лимиту формата
Оценка       → /api/evaluate списывает точный расход после отправки ответа
```

Ключевая мысль: живой диалог идёт напрямую из браузера в Gemini, поэтому фактический расход
видит только браузер — и верить ему нельзя. Отсюда схема «резерв + расчёт с зажимом»: браузер
может уточнить цифру, но не может заплатить меньше нижней границы, которую сервер считает сам
по времени сессии. Если браузер не отчитался вовсе, списывается вся бронь.
